# Evaluation

The dataset in `config/evaluation_cases.json` contains 13 distinct authored synthetic conditions: seven development cases and six reserved stress cases. The stress split adds a real synthetic causal parser change, an unmatched control with incomplete reproduction, conflicting authorization replicas, a replica unable to observe, inconsistent headers and a guard enabled during an assessment. Labels and variant IDs never appear in model prompts. The now-public cases are not independently collected real-world examples or a permanently unseen test set. A SHA-256 fingerprint identifies the exact dataset scored.

Each condition is executed three times with a rotated mode order: 39 actual assessments. **Single agent** runs the relevant specialist through every phase, including approved controls and reproduction; it is not restricted to an initial scanner signal. **Independent majority** runs the same relevant specialist, skeptic and risk assessor, but each sees only its own evidence and positions; peer packets are not delivered. The risk assessor has no direct tool permission and may abstain. Final CONFIRM/REJECT votes form the majority, with ties disputed. **Council** shares evidence, can recruit a capability and uses deterministic evidence adjudication. All modes have the same 48-request budget, per-agent permissions and 120-second deadline. Actual resource use differs and is reported. The comparison includes the council's extra observations and its conservative resolver; it does not isolate conversation from those factors.

Only `CONFIRMED` counts as a positive prediction. Precision and recall are calculated on adjudicable positive/benign cases using their ordinary denominators; an undefined denominator is null. A confirmation on a withheld/indeterminate case is an unsupported confirmation, not a demonstrated benign false positive; it is reported separately. Correct abstentions count `DISPUTED` or `NEEDS_HUMAN` on conditions labeled abstain. Exact accuracy requires the particular expected status. Development and stress scores are also reported separately. Wilson 95% intervals describe uncertainty in case-level exact accuracy, not validity for a real-world population. Confidence is a specialist belief, not a calibrated probability. Independent observers mean separately executed checks by different agents, not independent real-world data sources; the fixture and configured model are shared, so failures can remain correlated.

| Rule-mode process | Precision | Recall | Benign false positives | Unsupported confirmations | Correct abstentions | Exact accuracy | Tool requests |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Single specialist, full assessment | 100% | 100% | 0 | 1 | 6/7 | 10/13 | 27 |
| Independent final majority | 100% | 100% | 0 | 1 | 3/7 | 7/13 | 42 |
| Council | 100% | 100% | 0 | 0 | 7/7 | 13/13 | 43 |

All three processes handle the straightforward positive and benign conditions. The difference is withholding unsupported confirmation and retaining the right disposition under incomplete or conflicting observations. These are executed rule-mode results in [evaluation-results.json](evaluation-results.json). The council's 13/13 accuracy interval is approximately 77–100%. Tool totals include only executed permitted checks; blocked attempts are reported separately. Model tokens count completed responses reported by the provider; failed or canceled requests can have additional unreported provider cost. The offline benchmark uses actual FastAPI fixture handlers and a memory bus. Dashboard evaluation uses the local HTTP fixture. Timings exclude SLIM overhead and vary by machine. Zero model calls means rules were evaluated, not that model reasoning is free or validated.

`make evaluate` reproduces the offline benchmark. `/api/evaluation` defaults to rules even when assessments use a model. `/api/evaluation?use_model=true` explicitly runs configured model reasoning, and `scripts/validate_model.py --benchmark` records a real-provider model benchmark. Never present rule scores as model scores.

The before/after panel on an individual assessment retains the initial proposing vote and initial majority as a descriptive ablation. Those are separate from the independently executed evaluation baselines.

`scripts/verify_live.py` verifies real SLIM separately: ambiguous injection, access, patch reassessment, scope stop and mid-run guard change. It requires actual peer receipts, durable final events, expected resolver dispositions, and expert recruitment in the surprise case. [live-verification.json](live-verification.json) contains the records. [model-verification.json](model-verification.json) records local real-model acceptance and its explicit success/failure status. [model-slim-verification.json](model-slim-verification.json) records five passing real-model assessments over SLIM, separately from the rule benchmark. Earlier failures remain in model-attempts.json. Neither synthetic acceptance suite establishes broader security detection superiority.
